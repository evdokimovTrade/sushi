# ТаланД — сайт доставки

Тёмный сайт заказа для «ТаланД» («Просто вкусно», магазин всемирных продуктов). Доставка по юго-западу Петербурга: Аннино, Новоселье, Горелово, Красное Село.

Старый прототип в корне репозитория не трогали. Это приложение лежит в папке `taland`.

Цены суши и бургеров — **пример**, до прайса кухни. Цены шашлыка — **черновик** с меню «Шашлык на углях», на сайте помечено «цены уточняются». Вес порций шашлыка не указан, потому что его нет в исходнике. Телефон, адрес и ИНН на сайт не подставлялись: стоят пометки «добавим» и шаблоны для юриста.

У суши и бургеров ровно три фиксированных варианта. Допов, удаления ингредиентов и комбо нет. У блюд шашлыка 2–4 варианта, как в черновике. Гарниры, соусы, соленья и напитки — только количество.

## Стек

Next.js, React, Prisma, SQLite. Один процесс Node подходит для недорогого VPS. На Vercel файл SQLite не сохраняется между вызовами — для Vercel в разделе ниже есть переход на Postgres.

## Локальный запуск

Нужны Node.js 20+ и npm.

```bash
cd taland
cp .env.example .env
npm install
npm run db:setup
npm run dev
```

Сайт: http://localhost:3000  
Админка: http://localhost:3000/admin  
Пароль локального стенда берётся из `ADMIN_PASSWORD`. В `.env.example` это `change-me`. Перед публикацией замените.

`npm run db:setup` создаёт `data/taland.db` и записывает меню прототипа. Повторный `npm run db:seed` заново записывает меню и **не** удаляет заказы. Уже изменённые зоны и промокоды seed не затирает.

Проверки без браузера:

```bash
npm run check
npm run build
npm start
npm run test:flow
```

`test:flow` ждёт сервер на http://127.0.0.1:3000.

## Переменные окружения

Файл `.env.example` перечисляет их все. Секреты в git не коммитить.

| Переменная | Зачем |
| --- | --- |
| `DATABASE_URL` | SQLite. Надёжнее абсолютный путь `file:/полный/путь/taland/data/taland.db`. Скрипты `db:*` подставляют `file:$PWD/data/taland.db` сами. |
| `ADMIN_PASSWORD` | Пароль `/admin`. |
| `COOKIE_SECURE` | `true` только за HTTPS. На локальном http оставьте `false`, иначе браузер не сохранит вход. |
| `PUBLIC_BASE_URL` | Адрес сайта. Сюда ЮKassa возвращает покупателя. |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | Ключи **тестового** магазина. Пустые — сайт проводит тестовое подтверждение без списания денег. |
| `YOOKASSA_TEST_MODE` | По умолчанию `true`. Значение `false` без `YOOKASSA_ALLOW_LIVE=true` блокирует платежи, чтобы боевые ключи не включились случайно. |
| `YOOKASSA_ALLOW_LIVE` | Явное разрешение боевых платежей. Пока `false`. |
| `YOOKASSA_SEND_RECEIPT` | Передавать в платёж состав чека 54-ФЗ. |
| `YOOKASSA_VAT_CODE` | Код НДС. `1` — без НДС. |
| `YOOKASSA_PAYMENT_MODE` | `full_prepayment` — полная предоплата. |
| `YOOKASSA_TAX_SYSTEM_CODE` | Необязательно, если в магазине несколько систем налогообложения. |
| `YOOKASSA_RECEIPT_INTERNET` | Признак расчёта в интернете в чеке. |
| `ALLOW_MOCK_PAYMENTS` | Тестовая кнопка, когда ключей нет. С ключами она сама не показывается. |
| `AUTH_MODE` | `dev` — код входа на экране. `sms` — код уходит в шлюз и на экране не показывается. |
| `SMS_PROVIDER`, `SMS_HTTP_URL`, `SMS_HTTP_TOKEN` | Заготовка своего SMS-шлюза: POST JSON `{ phone, message }`. |
| `DEV_OTP_CODE` | Необязательный фиксированный код для своих автотестов. |

## Как устроен заказ

Корзина общая для всех страниц и лежит в браузере. Цены каждый раз берутся из базы, поэтому правка в админке видна сразу.

Район доставки задаёт минимальную сумму блюд и стоимость доставки. Эти цифры — пример, их меняют в админке на странице «Зоны». Скидка промокода считается от блюд, доставка не уменьшается.

В заказ пишутся имя, телефон, адрес, комментарий, промокод, способ оплаты и метки `utm_source` / `utm_campaign` со страницы, с которой человек зашёл. Для QR на машине ссылка такая: `https://домен/?utm_source=qr_auto`. Так же подходят `2gis`, `yamaps` и метки рекламы.

Оплата онлайн (карта или СБП) создаёт платёж ЮKassa и ведёт на их страницу. Вебхук `POST /api/payments/webhook` проверяет платёж запросом в ЮKassa и только потом ставит заказу статус «на кухне». Возврат покупателя на сайт тоже сверяет статус. Оплата при получении ставит статус «ожидает подтверждения менеджера». На кухню такой заказ попадает после кнопки «Подтвердить».

Цепочка статусов: ожидает оплаты или ожидает подтверждения → подтверждён → на кухне → готов → у курьера → доставлен. Отменить можно до доставки. Перескакивать статусы нельзя, кроме автоматического перехода оплаченного заказа сразу на кухню.

## Кабинет покупателя

Вход по телефону. В `AUTH_MODE=dev` код из 4 цифр показывается на экране тому, кто его запросил. Это замена SMS, пока нет договора со шлюзом. На публичном сайте так оставлять нельзя: кто введёт чужой номер, увидит код. Перед открытием поставьте `AUTH_MODE=sms` и свой `SMS_HTTP_URL`.

В кабинете — история, повтор заказа и сохранённые адреса.

## Админка

- Заказы: фильтры, источник, промокод, смена статуса, CSV.
- Колонки CSV: дата, №, источник, промокод, позиции, сумма, оплата, статус. Разделитель — точка с запятой, кодировка UTF-8 с BOM, время московское.
- Кухня: только заказы «на кухне», кнопка «Готово».
- Меню: название, три или положенные варианты, цены, фото, включено или выключено.
- Промокоды и зоны.

Примеры промокодов: `TALAND10` (−10%) и `NOVY500` (−500 ₽ от 1500 ₽).

## Чеки 54-ФЗ

В запрос платежа, если `YOOKASSA_SEND_RECEIPT=true`, кладётся объект `receipt`: телефон покупателя и позиции. Цена в чеке — за единицу, количество умножается на неё, сумма сходится с платежом. Скидка раскладывается по блюдам. Доставка, если она платная, уходит отдельной строкой как услуга. Чек выпускает сервис «Чеки от ЮKassa» в кабинете магазина — сайт сам кассу не подключает. Код НДС и признак способа расчёта задаются переменными выше.

## Домен и VPS

Пример для Ubuntu, процесс слушает порт 3000.

```bash
cd /var/www/taland
npm ci
npm run db:setup
npm run build
```

systemd, файл `/etc/systemd/system/taland.service`:

```
[Service]
WorkingDirectory=/var/www/taland
Environment=NODE_ENV=production
EnvironmentFile=/var/www/taland/.env
ExecStart=/usr/bin/npm start
Restart=on-failure
```

В `.env` на сервере: абсолютный `DATABASE_URL`, новый `ADMIN_PASSWORD`, `PUBLIC_BASE_URL=https://ваш-домен`, `COOKIE_SECURE=true`.

Caddy как обратный прокси сам получит сертификат:

```
ваш-домен {
  reverse_proxy 127.0.0.1:3000
}
```

DNS: A-запись домена на IP сервера. Пока запись не разошлась, ЮKassa не сможет вызвать вебхук.

Папку `data/` включите в бэкап: там SQLite с заказами.

## Боевая ЮKassa потом

1. В кабинете ЮKassa создайте боевой магазин, не тестовый.
2. Включите «Чеки от ЮKassa» и систему налогообложения. Сверьте `YOOKASSA_VAT_CODE`.
3. HTTP-уведомления: `https://ваш-домен/api/payments/webhook`, событие `payment.succeeded`.
4. В `.env` впишите боевые `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY`.
5. Поставьте `YOOKASSA_TEST_MODE=false` и `YOOKASSA_ALLOW_LIVE=true`.
6. `ALLOW_MOCK_PAYMENTS=false`.
7. Перезапустите сервис и проведите платёж на 1 ₽, затем верните его.

Пока `YOOKASSA_ALLOW_LIVE` не `true`, боевой режим не включится, даже если ключи уже лежат в `.env`.

Тестовый магазин подключается так же, но `YOOKASSA_TEST_MODE` остаётся `true`, а `YOOKASSA_ALLOW_LIVE` — `false`. Тестовые карты смотрите в документации ЮKassa, здесь они не продублированы, чтобы не устареть.

## Postgres вместо SQLite

Для Vercel или нескольких процессов файл SQLite не подходит.

1. Поднимите Postgres (Neon, Supabase или свой).
2. В `prisma/schema.prisma` замените `provider = "sqlite"` на `provider = "postgresql"`.
3. `DATABASE_URL` — строка Postgres.
4. `npx prisma db push && npm run db:seed`.

Остальной код тот же.

## Что сознательно не выдумано

Нет отзывов, нет телефона с черновика меню, нет ИНН, юридического адреса и названия юрлица. Страницы оферты, персональных данных и доставки — шаблоны с пометкой, что их заполняет заказчик.
